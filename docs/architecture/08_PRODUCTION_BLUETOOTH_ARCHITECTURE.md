# Production Bluetooth Architecture

## Purpose

Documents the production BLE design for two Universal Pods + dual EMG bands per player, and states plainly what's already real vs. what's still a documented gap. Written alongside `app/etl/receiver/bleak_transport.py` (a real `bleak`-based `BLETransport`, added this pass — see `docs/development/06_REPO_HYGIENE_REPORT.md`'s sibling platform-lock work) and `docs/research/UNIVERSAL_POD_MOUNTING.md`.

## What already exists and is real

The ETL pipeline's Bluetooth boundary was already well-designed before this pass — `app/etl/receiver/transport.py`'s `BLETransport` `Protocol` is the sole dependency `BLEReceiver` has on Bluetooth at all, with two implementations: `FakeBLETransport` (in-memory, for tests/local dev) and, as of this pass, `BleakBLETransport` (real `bleak` GATT calls — connect/disconnect/notify/reconnect — never exercised against physical hardware, since none exists in this environment).

- **Reconnection**: `BLEReceiver.connect()` already retries per device up to `BLE_RECONNECT_MAX_ATTEMPTS` (default 3) with `BLE_RECONNECT_BACKOFF_SECONDS` backoff (`app/config/etl_config.py`), raising `BLEConnectionError` only after exhausting attempts. `BleakBLETransport` implements this exact policy against real `bleak.BleakClient.connect()` calls, and additionally wires a real `disconnected_callback` so an *unexpected* mid-session disconnect (not just a failed initial connect) reaches `BLEReceiver` via the existing `DisconnectCallback` hook.
- **Ordering**: `sequenceNumber` (BACKEND_SPECIFICATION.md §8/§19), not arrival order or `serverReceivedAt`, is the authoritative signal for reconstructing what happened when — already the documented convention on the Firebase side, and now enforced identically on the Cloud Function side (`functions/src/callable/ingestLiveTick.ts` rejects a tick whose `sequenceNumber` doesn't strictly advance past what's already stored, treating a stale/redelivered tick as an idempotent no-op rather than corrupting the "latest" projection).
- **Dropped packets / data completeness**: `sessions.dataCompleteness` (§1.8) is the honest, non-hidden signal for gaps — a session with buffered-and-recovered ticks or a genuinely lost stretch both surface here, rather than either case silently looking identical to a fully-clean session. This is a safety-relevant honesty requirement (§19), not cosmetic.
- **Synchronization across devices**: `app/etl/synchronization/{synchronizer,group_synchronizer}.py` already aligns packets from multiple concurrently-active devices (two Pods + two EMG bands) into one `SynchronizedFrame` per synchronization group, independent of Bluetooth-layer concerns — this stage doesn't know or care that its inputs arrived over BLE at all, which is the right separation of concerns.

## What's a genuine, documented gap — not silently worked around

- **Latency monitoring** is only half-built: `ingestLiveTick`'s `serverReceivedAt` (Cloud-Function server timestamp) vs. `tickTimestamp` (laptop-reported) delta is exactly the signal §21.2 describes for detecting delivery latency — but nothing currently *computes or surfaces* that delta anywhere (no dashboard, no alert, no metric). The data to do this exists in every stored tick; the monitoring itself doesn't exist yet. A `deviceHeartbeatMonitor`-style scheduled check (already built, `functions/src/scheduled/deviceHeartbeatMonitor.ts`) is the natural place to add a latency-threshold alert alongside its existing silence-timeout check, once real timing data from real hardware shows what a meaningful threshold is — this pass does not invent one from nothing.
- **Two Pods per player, not one**: `BLETransport`'s interface is already multi-device-capable (`connect(device_id, ...)` per logical device, `BLEReceiver` manages a `Set` of connections) — no interface change is needed to support two Universal Pods per player. But `app/config/etl_config.py` only defines one `SMART_POD_DEVICE_ID` logical identifier; supporting two concurrently active Pods per player needs per-instance logical IDs (e.g. `smart_pod_left`/`smart_pod_right`, mirroring the already-established `left_lower_limb`/`right_lower_limb` bilateral-group convention used throughout `app/risk_engine`), which is a small, additive config change, not made in this pass since it wasn't requested as code and the exact naming is a product/hardware-provisioning decision.
- **`BleakBLETransport`'s two hardware-specific unknowns** (the real BLE address per logical device, and the real GATT notification characteristic UUID) are constructor parameters, not hardcoded — because this repository has no provisioned GATT profile for Vikzar's actual hardware to hardcode. This is the single biggest reason "untested against physical hardware" is not a formality: without real firmware's actual UUIDs, this code cannot be exercised end-to-end no matter how correct its logic is.

## Bottom line

The BLE *architecture* — the interface boundary, the retry/reconnect policy, the ordering/completeness signals — was already sound and required no redesign. What was missing was a real (if hardware-untested) implementation of that interface, which now exists. What remains before a live pilot is entirely hardware-dependent: real device addresses, a real GATT profile, and time with physical Pods to validate the retry/backoff constants against real-world BLE range and interference, none of which can be produced by writing more code.
